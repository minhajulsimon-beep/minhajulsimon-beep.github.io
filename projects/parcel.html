01 / CONTEXT

Tracking a parcel isn't always chronological.

Delivery scans can be repeated, delayed, or written to a later batch despite having an earlier event timestamp. A naive pipeline can count the same scan twice or report the wrong parcel status. This project turns shipment and scan CSV files into a consistent reporting layer without hiding the problematic input rows.

The most useful part of an SLA report is often the logic behind its numbers.
02 / SYSTEM DESIGN

From batches to a parcel lifecycle.

The pipeline ingests synthetic shipment and scan batches, validates fields, and stores accepted records in SQLite. SQL window functions rebuild a parcel's most recent event using the event timestamp rather than file ingestion order. The resulting lifecycle view supports HTML, CSV, and JSON reports.

CSV source filesShipments + two scan batches→Python validationAccepted / rejected records→SQLite + SQLEvent-time lifecycle→ReportsHTML / CSV / JSON

All demo input data is synthetic. Carrier names, regions, and SLA results are examples for evaluating pipeline behavior, not real customer data.

03 / ENGINEERING CHOICES

Designed for the awkward cases.

  • Idempotent ingestionRepeated scan IDs with identical values are skipped; conflicting reuse of an event ID is rejected.
  • Event time over arrival orderLatest status comes from when the scan happened, not which file reached the pipeline last.
  • Quarantine invalid rowsBad timestamps, unknown event types, and invalid parcel IDs are saved with their rejection reasons.
  • Precise KPI definitionsOn-time rate is calculated over delivered parcels. Open, overdue parcels are counted separately.
04 / EVIDENCE

Repeatable demo, automated checks.

Run the included demo with python run.py demo. It produces a standalone HTML report plus CSV and JSON output files. The repository documents 11 tests for repeated ingestion, event-ID conflicts, late scans, invalid timestamps, rejected-row handling, and report consistency. GitHub Actions runs tests and a fresh demo on pushes and pull requests.

In the checked-in example, 598 of 800 parcels were delivered, 431 of those deliveries were on time, and the delivered-only on-time rate was 72.1%. These figures are derived from synthetic data with a fixed reporting reference time.

05 / REALISTIC SCOPE

What comes next.

This is a batch-oriented portfolio project, not a production carrier integration. It does not ingest live logistics APIs, and its reporting reference timestamp is used for overdue calculation rather than full historical state reconstruction.

Potential extensions include ingestion watermarks, scheduled refresh, stronger state-transition validation, and PostgreSQL-backed reporting for larger datasets.
